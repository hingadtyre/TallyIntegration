## TallyPrime: verified local connection requirements

1. On the customer's Windows computer, open TallyPrime and load the intended company. Tally must remain running on the configured port; at least one company must be loaded. The integration exchanges XML using HTTP POST. [Tally integration prerequisites](https://help.tallysolutions.com/pre-requisites-for-integrations/)
2. Prefer the installed product's **F1 (Help) → Settings → Connectivity → Client/Server Configuration** screen when available. Select HTTP Server or Both, then set port **9000** or another unused port. Tally's October 2026 integration guide explicitly supports a same-computer endpoint such as `http://127.0.0.1:9000`. [Tally connectivity guide](https://help.tallysolutions.com/building-tunnel-based-connectivity-for-tallyprime-integrations/)
3. Another documented route is **Alt+Z (Exchange) → Configure → Client/Server Configuration**. Save and follow Tally's restart prompt; the synchronisation guide explicitly calls for a restart after this configuration. Confirm the displayed port under **F1 → About → Connectivity** and reload the company after restarting. This uses the connectivity section only; Tally-to-Tally synchronisation, Tally.NET setup and public-IP prerequisites are not requirements for Stockbridge's same-computer XML reader. [Tally client/server configuration, updated November 6, 2026](https://help.tallysolutions.com/set-up-for-data-synchronisation/)
4. The August 2025 XML guide instead names **F1 → Settings → Advanced Configuration**, then enabling HTTP on default port 9000. It lists ODBC separately as optional. Record the installed Tally version and actual menu labels; the reviewed sources do **not** establish a reliable 6.x-versus-7.0 menu split. [Tally XML configuration](https://help.tallysolutions.com/xml-integration/)
5. Put the matching endpoint in Stockbridge Settings, then run **Connections → Check & discover companies**. A browser response alone proves reachability; an actual XML read and comparison with the same company/reporting period are needed to validate data. The official guide makes this distinction. [Tally request verification](https://help.tallysolutions.com/building-tunnel-based-connectivity-for-tallyprime-integrations/)

Tally's newer guide says native JSON integration starts with Release 7.0. Stockbridge currently uses XML; that statement does not establish a minimum supported Tally version for this adapter. Live compatibility and stock/report semantics still require verification. [Tally format/version guidance](https://help.tallysolutions.com/building-tunnel-based-connectivity-for-tallyprime-integrations/)

Record the intended source godowns even if the customer has not enabled multiple godowns: Tally uses an internal **Main Location** in that case. A company-wide balance does not establish the stock available at a particular marketplace location. Compare source quantities against the same company, date, base unit and godown during onboarding; do not create or alter accounting records solely to make a test pass. [Tally godown FAQ](https://help.tallysolutions.com/tally-prime/godowns-locations/godowns-locations-faq-tally/)

## Flipkart authorization model background

Seller login does not grant API access. Seller self-access details must not be shared with providers; providers managing sellers need third-party applications. [Application registration](https://seller.flipkart.com/api-docs/FMSAPI.html#application-registration)

| Operator       | Documented registration                                                                                                                                                             |
| -------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Seller         | Manage Profile → Developer Access → Create New Access; enter name/description and submit.                                                                                           |
| Partner/vendor | Register at the partner portal as an API partner; await verification. Then Profile → Manage API Access → Create Application; supply name, description and valid HTTPS callback URL. |

[Flipkart registration steps](https://seller.flipkart.com/api-docs/FMSAPI.html#application-registration)

Self-access uses `client_credentials`: the seller's application ID/secret obtain an access token directly, without the third-party browser callback. This is the local route being implemented and evaluated on this branch. Third-party onboarding instead sends the seller through Flipkart's authorization page with `Seller_Api` scope; it requires returned `state` validation, a provider-credential code exchange and installation binding. Neither route asks Stockbridge to collect the seller login password. [Token flows](https://seller.flipkart.com/api-docs/FMSAPI.html#generating-access-tokens)

The documented scope does not establish separate inventory-read/order-read/inventory-write permission switches. Review the actual consent and returned scope. [Authentication examples](https://flipkart.github.io/fk-api-platform-docs/docs/intro)

No provider registration, approval or callback deployment has been evidenced in this repository. Those are prerequisites if the provider-managed route is used. A local dashboard address is not its required registered HTTPS callback. Self Access has its own seller registration; it does not mean API access without any application registration. [Application registration](https://seller.flipkart.com/api-docs/FMSAPI.html#application-registration)

Use returned expiry values instead of assuming a token stays valid. The documented Self Access response contains `access_token`, `token_type`, `expires_in` and `scope`; obtain replacement access through the same client-credentials flow. Do not assume it returns the refresh token shown in third-party authorization examples. Verify actual responses with approved application access. [Token and expiry documentation](https://seller.flipkart.com/api-docs/FMSAPI.html#generating-access-tokens)

Flipkart's separate API Hub includes sandbox-host examples while the seller documentation shows production-host examples. Choose one intended environment deliberately; do not paste samples indiscriminately. Seller registration alone does not provide sandbox access; API questions can be raised through the seller/partner portal's API GA support route. [API Hub examples](https://flipkart.github.io/fk-api-platform-docs/docs/intro), [Flipkart FAQ](https://seller.flipkart.com/api-docs/FAQ.html)

### Multiple-customer distribution clarification, 2026-11-08

The official guides distinguish seller-owned self-access from a vendor operating APIs for other sellers. They restrict self-access to the seller's own use and prohibit sharing those credentials with third-party partners. The user confirmed that HingadTyre itself owns Stockbridge and uses it for its own seller account; that scope matches the documented Self Access category, subject to Flipkart's pending application approval. This does not settle eligibility for distributing Stockbridge to independent sellers, and token acceptance alone cannot settle that separate question. [Registration and authorization](https://seller.flipkart.com/api-docs/FMSAPI.html#application-registration)

The user initially accepted a provider-managed product with a small hosted HTTPS authorization/token service on 2026-11-08, recorded in [ADR 0003](../adr/0003-provider-managed-flipkart-authorization.md). Later that day, the user requested the separate `codex/flipkart-self-access` branch to inspect the seller UI and implement local seller-owned authentication, recorded in [ADR 0004](../adr/0004-seller-owned-flipkart-self-access.md). This changes the branch's implementation direction, not Flipkart's rules. A provider service remains the alternative if the intended arrangement requires partner access. Never distribute a shared confidential provider secret in an installer; native copies cannot keep it confidential. [RFC 8252 section 8.5](https://www.rfc-editor.org/rfc/rfc8252#section-8.5)

Browser evidence on 2026-11-08: the HINGADTYRES account exposed **Profile > Developer Access > Self Access > Create New Access**. The form requested Application Name, Description and Website Domain, extending the name/description fields listed in the public guide. The user submitted **Stockbridge Local**, **Tally stock integration** and **https://github.com/hingadtyre/TallyIntegration**. The table now shows **Pending**, and the confirmation said **Sent for Approval**, with contact to the registered phone/email within seven working days. That is observed review guidance, not a guaranteed approval date. Registration submission is established; application approval, usable credentials, token access, API seller identity and listing responses remain unverified. The Copy control returned no usable value during inspection. The local authentication flow needs neither a purchased domain nor a hosted authentication service.

The installer journey still has no Stockbridge invitation, activation code or separate signup/approval. Eligible sellers create their own application for this branch's route and enter its credentials locally; the provider-managed alternative uses seller consent. Both require verified seller identity and stock mappings before publication. See [open installer onboarding](../design/architecture.md#open-installer-onboarding).

## Verified listing, inventory and order contracts

These are implementation inputs checked on 2026-11-08, not authenticated response evidence. Keep the production and sandbox hosts explicit. Paths below include the `/sellers` prefix shown by the current API Hub.

| Operation                        | Documented contract and implementation consequence                                                                                                                                                                                                                                                                                                                                                                                                                                                                               |
| -------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Discover listings                | `POST /sellers/listings/v3/search` returns batches of 500. Start with a null `page_id`; continue using `next_page_id` while `has_more` is true. Omitting the status filter requests both active and inactive listings. The published schema also contains the spelling `lisitng_status` and a singular-looking `listings` object; resolve these inconsistencies with authenticated examples before finalizing the parser. [Listing search](https://flipkart.github.io/fk-api-platform-docs/docs/mp-api_versioned/listing-search) |
| Read listing details             | `POST /sellers/listings/v3/details` accepts at most 10 `sku_ids`. Handle `available`, `unavailable` and `invalid` results. Details include listing/product IDs, shipping `packages`, and location ID/status/`inventory`/`pending_inventory`. The schema does not establish a sellable pack size or the accounting relationship between the two inventory fields. [Listing details](https://flipkart.github.io/fk-api-platform-docs/docs/mp-api_versioned/get-listing-details)                                                    |
| Read product and seller evidence | `POST /sellers/listings/v3/product/search` returns up to 20 listings per `batchNo`, starting at zero, filtered by `internalState`; results include `sellerId`, listing ID, product ID and SKU. This can corroborate seller identity for returned listings, but is not evidence of a general identity lookup for an empty account. [Product search](https://flipkart.github.io/fk-api-platform-docs/docs/mp-api_versioned/product-search)                                                                                         |
| Read back known listings         | `GET /sellers/listings/v3/:skuIds` returns location inventory along with listing details. Treat unavailable or invalid entries separately from a successful quantity observation. [Listing reads](https://flipkart.github.io/fk-api-platform-docs/docs/mp-api_versioned/get-listings)                                                                                                                                                                                                                                            |
| Update location stock            | `POST /sellers/listings/v3/update/inventory` accepts at most 10 SKUs, with product ID and location-specific nonnegative inventory. HTTP 200 can contain failed SKUs: inspect individual statuses/errors and then read back the intended destination. [Full endpoint](https://flipkart.github.io/fk-api-platform-docs/docs/mp-api_versioned/update-inventory), [per-SKU result contract](https://seller.flipkart.com/api-docs/listing-api-docs/v3/UpdateListingsInventoryAPI.html)                                                |
| Discover orders                  | `POST /sellers/v3/shipments/filter` supports `preDispatch`, `postDispatch` and `cancelled` types, status/location/date filters including `modifiedDate`, and `hasMore`/`nextPageUrl` pagination. Verify complete time and page coverage before marking reconciliation current. [Shipment search](https://flipkart.github.io/fk-api-platform-docs/docs/mp-api_versioned/search-pre-dispatch-shipment-post)                                                                                                                        |
| Attribute known order items      | `GET /sellers/v3/shipments` accepts one identifier kind per request: shipment IDs, order IDs or order-item IDs, with a documented maximum of 100. Responses expose shipment `locationId` and order-item ID, listing ID, SKU, status and quantity. This resolves known records; it is not discovery. [Order detail lookup](https://flipkart.github.io/fk-api-platform-docs/docs/mp-api_versioned/get-shipment-details-by-internal-id)                                                                                             |

Implementation inference: polling only records currently marked `APPROVED` can miss an order that advanced while the application was offline. The connector needs a verified reconciliation strategy covering those transitions and must not silently treat an incomplete window as zero sales. The approved activation-generation and deduplication rules remain in the [architecture](../design/architecture.md#allowance-activation-and-sales-accounting); a fixture or a known-order lookup alone cannot establish production order coverage.

Shipping packages are not automatically physical pack units. For this customer's tyres, confirm one tyre per package and reconcile the listing's product/set evidence before using package count as pack size. Preserve the distinction in [GLOSSARY](../../GLOSSARY.md). Likewise, neither SKU text nor a seller display name establishes a stable account/listing identity.

The consulted public pages reference an Onboarding API for location IDs but do not establish a standalone seller-profile/location-discovery endpoint. Obtain the approved contract or authenticated evidence through Flipkart's API GA support route. Do not invent an endpoint, assume a seller ID from a token's undocumented contents, or fabricate locations for an empty account. [Location-ID requirement](https://seller.flipkart.com/api-docs/listing-api-docs/v3/UpdateListingsInventoryAPI.html), [support and environment guidance](https://seller.flipkart.com/api-docs/FAQ.html)

## What the repository currently implements

- The Tally URL validator allows only `127.0.0.1`, `localhost` and IPv6 loopback, with no credentials/path/query/fragment. The backend also binds to `127.0.0.1`. Same-computer installation is therefore a current application constraint, not a claim that Tally itself cannot support a private network. [Tally adapter](../../src/adapters/tally.ts), [backend startup](../../src/server/main.ts)
- Live/sample state is separate. The Windows x64 portable pilot bundles Node v24.22.2, an external data path, start/stop/status launchers and an offline guide. The pre-self-access baseline delivered in `f2ec672` passed 16 extracted-package checks, including backup/restore and restart/persistence without a development toolchain or real external accounts. This is historical pilot evidence; the changed package needs its own check. See the [release-readiness audit](../release-readiness.md#current-deliverable). [Backend startup](../../src/server/main.ts)
- The branch adds local Self Access token acquisition, current-user Windows-protected credential storage and a connection panel. **Save credentials for later** replaces the local saved credentials without contacting Flipkart; **Check saved access** can verify them after application approval. Saving is separate from token verification, which is separate from seller identity/import. One credential set is supported and demo mode never saves it or contacts Flipkart. `/api/publish` still explicitly returns an unavailable error. Authenticated seller/import, durable publication and recovery remain application work. [HTTP routes](../../src/server/http.ts), [current delivery status](../../README.md)
- The adapter's first stock view is company-wide. Company identifiers, balance period, base units, godowns, marketplace locations and per-listing pack evidence must be verified before publication. Browser evidence for one listing is insufficient to validate all mappings. [Customer setup](../customer-setup.md), [Flipkart validation](flipkart-validation.md)
