## Accepted authorization model and remaining setup

The user initially selected provider-managed authorization on 2026-11-08, then requested a separate branch to test and implement seller-owned Self Access. [ADR 0004](../adr/0004-seller-owned-flipkart-self-access.md) records the branch's change from [ADR 0003](../adr/0003-provider-managed-flipkart-authorization.md). The seller registers its own application and supplies its Application ID and Secret to the local backend. The current Windows user protects the saved credentials with DPAPI outside SQLite/backups. No hosted Stockbridge callback/service is required for this token flow.

The user confirmed that HingadTyre owns Stockbridge and uses it for its own seller account. That scope matches the documented Self Access category; Flipkart's application approval remains pending. **Technical token support does not establish independent-seller distribution eligibility.** Flipkart directs partners/aggregators to third-party applications. Obtain clarification before treating this internal route as a general customer-distribution route. If a provider application is required, its registration, hosted authorization and seller consent remain unimplemented external/application work.

**Save credentials for later** protects the entered credentials locally without any Flipkart request. A successful save replaces any previous saved credentials, clears their cached token/check state and leaves the new access unverified. **Verify and save credentials** instead requires a successful token check before replacement; a failed check preserves the previous credentials. After Flipkart approves access, **Check saved access** checks the saved application. Local saved/verified states must not be presented as Flipkart's application approval state.

The panel's **API credentials verified** status means the token endpoint accepted the application credentials and returned a validated token/expiry. It does not prove authenticated seller identity, location scope, listing permission or successful stock publication. Only one local credential set is supported; changing it must not silently attach another seller to existing inventory records. **Disconnect locally** removes local credentials, not the Flipkart application. Tokens exist only in memory and are never returned to dashboard code or ordinary backups. An offline SQLite restore retains the same workspace's existing protected credential file, but restarting requires **Check saved access**; a moved/new workspace or another Windows user needs credential setup again. Demo mode does not save credentials or call Flipkart. The [customer setup guide](../customer-setup.md#optional-verify-seller-owned-flipkart-api-access) describes the available steps and current limits.

Local verification must cover save-only operations making no Flipkart request, replacement clearing verification, rejected credentials, expiry/replacement, redirects, timeout/malformed responses, unavailable protection, failed replacement preserving prior saved data, disconnect races and secret exclusion from outputs/logs/backups. Record the exact final tests/package separately in [release readiness](../release-readiness.md). An injected transport or real DPAPI round trip does not establish live Flipkart token acceptance.

## Publication validation

Before enabling publishing:

1. Confirm eligibility for the selected authorization model and complete the intended customer's application registration/authorization. Verify credential handling, actual token acceptance, seller identity and account isolation before using the connection for stock operations.
2. Read authenticated account/location identities and listing details; compare the inspected sample SKU to its API package entries and catalog set evidence.
3. Verify pack evidence for each mapping and source-to-marketplace stock locations. Shipping packages only stand for tyres where one tyre per package is confirmed.
4. Verify approved-order discovery, complete pagination/time coverage, exact listing and location attribution, quantities, repeats and cancellation behaviour.
5. Implement and test activation baselines, durable deduplicated receipts, serialized publication attempts, per-SKU outcomes, uncertainty/read-back recovery and stale-source checks before a reviewed live test.
