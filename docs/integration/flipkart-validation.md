**Updated 2026-11-20. The application completed two read-only imports of 217 listings. All had shipping package counts and 137 had a stock location. Separate catalogue evidence established a sellable quantity for all 190 active tyres.**

## Order evidence for Tally billing review

Stockbridge reads order lines using [shipment search](https://flipkart.github.io/fk-api-platform-docs/docs/mp-api_versioned/search-pre-dispatch-shipment-post) and its [documented pagination](https://flipkart.github.io/fk-api-platform-docs/docs/mp-api_versioned/search-pre-dispatch-shipment-get). Each review covers up to 31 days of order dates for the selected account. Search requests explicitly select seller fulfilment (`NON_FBF`) and query normal and self-ship shipments separately before and after dispatch. The reader excludes held, cancelled, return and replacement lines. Express and other fulfilment profiles are outside this review. A page failure, inconsistent order-item identity or search reaching the provider limit invalidates the review. An empty result only describes the requested scope. See the [seller dispatch and search limits](https://seller.flipkart.com/api-docs/order-api-docs/v3/PostShipmentSearch.html).

The import keeps the order ID, order-item ID, listing ID, exact SKU, dispatch location, quantity and order date. Repeated observations of the same line count once. For invoice-reference reviews, eligible packed or later shipment lines can also receive a confirmed invoice number. The [seller invoice reference](https://seller.flipkart.com/api-docs/order-api-docs/OMAPIRef.html#get-v3-shipments-shipmentids-invoices) documents JSON invoice numbers and order-item membership, while the [current invoice API](https://flipkart.github.io/fk-api-platform-docs/docs/mp-api_versioned/get-invoices-pdf-from-esi) describes PDF. Stockbridge requests JSON and accepts a number only when both the shipment and order line agree. Unissued invoices and PDF-only responses leave the invoice reference unavailable. The reader never generates a label or invoice.

Flipkart's [order-item model](https://github.com/Flipkart/flipkart-seller-api-java-sdk/blob/master/docs/OrderItem.md) and [shipment model](https://github.com/Flipkart/flipkart-seller-api-java-sdk/blob/master/docs/Shipment.md) mark classification flags as optional. An identified line with missing hold, status, replacement or courier-return evidence is retained for review with eligibility unverified. The reader also accepts the current and older spellings of the replacement flag. It interprets offset-free ISO timestamps in Indian standard time.

The adapter is exercised with local fixtures. Live coverage across order states, seller access, pagination and JSON invoice availability still require a seller-authorized read and comparison with Seller Hub. The review does not control marketplace stock, fulfilment or the Limited sales policy.

Separate [return-package feasibility research](flipkart-return-package-research.md) records the 2026-11-18/19 Seller Hub, API and official Ekart browser checks. All 28 original package tracking numbers across six courier-return orders exposed individual RTO histories, including different states and times within an order item. Supported automated carrier access, authoritative event meanings, customer-return package coverage and physical seller receipt remain unverified. Carrier hub receipt is not seller-confirmed receipt. Returns are not implemented in Stockbridge; the user put implementation on hold on 19 November while accepting the research and Postman changes.

## Implemented accounts and imports

The [seller-owned Self Access route](../adr/0004-seller-owned-flipkart-self-access.md) uses direct token requests and Windows current-user credential protection. HingadTyre confirmed internal own-account use. Independent-seller distribution eligibility remains separate; a provider-managed route would need its own approved registration, consent and hosted callback.

Marketplaces contains explicitly added account tiles. Each new account owns a protected credential folder; saved legacy primary credentials are adopted in place. Save without verification makes no external request. Verify and save checks token access before replacement; a failed replacement retains previous saved credentials. Tokens stay in memory and secrets are excluded from API responses, logs and database backups.

Each completed import checks seller IDs when provided. If the provider omits the seller ID, the first complete import establishes ownership through its authenticated listing and product identities. Subsequent imports require continuity, and conflicting accounts and recreated protected identities are rejected. An empty new account cannot establish ownership. Restart and credential changes require a fresh import. An unsuccessful refresh leaves the last catalogue visible and prevents publishing against unverified access. Mapped accounts refresh on the catalogue interval and on demand. Demo uses local sample data.

## Apply, policies and recovery

Before an Inventory stock update, the fresh detail response must confirm an active listing and enabled destination. A missing or unrecognized listing status blocks the update even when the previous import showed Active. Flipkart documents the status and archive values in [listing details](https://flipkart.github.io/fk-api-platform-docs/docs/mp-api_versioned/get-listing-details).

Each Apply saves a durable attempt before sending, checks fresh values and conflicts, preserves the unedited companion price and submits only that edit. It checks per-SKU outcomes and reads back the edited value. A definitive rejection stays failed. For stock, a lost submission reply, warning, ambiguous response or in-progress response leaves the previous request unresolved. An observed quantity alone cannot establish that the old request finished. The exact successful per-SKU result and a fresh listing read serve separate purposes. A recorded completed stock request with inconclusive readback can enter seller-reviewed recovery. The documented inventory response distinguishes a successful update for the individual SKU from failures and warnings. An HTTP-level acknowledgement alone is insufficient. [Flipkart inventory response](https://flipkart.github.io/fk-api-platform-docs/docs/mp-api_versioned/update-inventory). An unresolved outcome blocks further edits to that listing. In-flight attempts become uncertain after restart and are not automatically replayed.

Imported destinations update Inventory observations without granting a Tally mapping or pack verification. Stock Apply preserves holds and allowances, including when Pause is selected. Update once retains the automation setting; Pause Tally sync and update saves Pause; price-only changes leave automation untouched. Positive live stock under Limited sales is blocked until order reconciliation exists or the seller explicitly returns that destination to Auto. The confirmed policy change retains Pause and sends no stock. Inventory publishes reviewed quantities and recalculates confirmed, eligible destinations after Tally changes. Newly verified orders also trigger decrease checks across eligible listings sharing an item. All Tally calls are reads.

Schema 4 introduced durable destination mapping choices and pending Tally changes. Schema 5 added per-company and per-account billing rules and seller-confirmed order-to-bill links. Schema 6 records the stock-history baseline and observed order obligations. Schema 7 persists pending checks for shared listings and stock request completion evidence. Offline restore supports schema 2–7 backups. It keeps current billing decisions for configured company/account pairs present in the restored workspace and recovers saved rules and confirmations for other pairs. Conflicting assignments refuse replacement. Restore clears the stock baseline confirmation, pauses listings, disables company automation and marks unfinished updates uncertain. The seller must reconcile and confirm the baseline again before publishing reconciled stock. Credentials stay outside the database.

## Order history for stock publication

Stockbridge reads the seller's selected history start through the time of the check. Each search covers up to 31 days. Adjacent windows share their cutoff and order-item IDs remove duplicates. Each window includes the regular and self-ship variants of the seller-fulfilled NON_FBF service. Pre-dispatch orders are requested separately with hold on and off. Post-dispatch searches include return-requested and returned lines. Cancellation searches include buyer, seller and marketplace cancellations. The separate billing review retains its 31-day limit. [Shipment search contract](https://flipkart.github.io/fk-api-platform-docs/docs/mp-api_versioned/search-pre-dispatch-shipment-post) and [seller search guide](https://seller.flipkart.com/api-docs/order-api-docs/v3/PostShipmentSearch.html).

The stock read follows each continuation page. At the 5,000-shipment limit it repeats the affected search in shorter windows. Malformed, failed or conflicting reads and a saturated search at a single instant prevent a complete result. A previously seen line that disappears while splitting a search is flagged for review. A held, replacement, returned, courier-return or unfamiliar line retains its identity for review. Only an identified buyer or marketplace forward cancellation with a cancellation timestamp and clear fulfilment flags qualifies as cancelled stock evidence. A previous dispatch or return observation conflicts with an unshipped cancellation and requires reconciliation. A seller cancellation can indicate a shortage. A carrier's return status cannot confirm sellable physical stock. [Flipkart order lifecycle](https://seller.flipkart.com/api-docs/order-api-docs/OMAPIOverview.html).

The supported stock pool covers seller-fulfilled normal and self-ship orders. Sellers must account for older outstanding orders before choosing a start and confirm any stock used by other fulfilment programmes separately. The public search contract gives no historical retention guarantee or atomic cut-off shared with a stock write. An authenticated pilot must compare the covered dates, order identities, held and cancelled lines, return states and totals against Seller Hub before relying on production coverage. Stockbridge has no evidence of orders that the provider silently omitted from every read.
