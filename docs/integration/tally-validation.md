# Tally read-only adapter validation

The adapter exports companies, stock items, ledgers and selected-ledger sales bill evidence. It never imports, creates, edits or deletes Tally records. The adapter uses a local HTTP listener and rejects redirects and non-loopback destinations.

The request shape follows Tally's documented [XML envelope, collection export and static variables](https://help.tallysolutions.com/xml-integration/). The [collection XML examples](https://help.tallysolutions.com/how-to-write-remote-compliant-tdl-reports-in-tdl/) use `NATIVEMETHOD` for fetched fields and `METHOD` for computed values. [Third-party extraction](https://help.tallysolutions.com/integration-initiated-from-tpas/) documents HTTP/XML collection access and the usual port 9000. [Inventory master examples](https://help.tallysolutions.com/sample-xml/) document stock-item base units. These sources establish the general interface, not successful integration with the user's installed Tally version.

The code asks for company and item GUIDs, which must be verified for stability across rename, restore and reconnect on the installed version. Missing or duplicate GUIDs block the import. Names are display values and are used only for the required `SVCURRENTCOMPANY` scope, never as internal identities.

Stock export sets `SVCURRENTCOMPANY` and `SVTODATE`. The default closing balance uses today's Indian book date regardless of the computer's time zone. Calculated publication reads both closing balances and the sales vouchers through the same Indian book date. A check that crosses Indian midnight must be repeated before dispatch. An embedded computed field, `StockbridgeCompanyGuid : $GUID:Company:##SVCurrentCompany`, projects the selected company GUID onto each stock row and must match the requested GUID. Company discovery also runs before and after the export. If that projection is unavailable or a company identity changes, the adapter refuses the read. These checks are not an atomic snapshot of a changing Tally session. Each company must pass independently. A rejected company export leaves its previous observations available for display and its stock blocked until verification. Other verified company exports can still be used. A failed discovery affects the entire endpoint.

The tests exercise real local HTTP requests against constructed XML fixtures: successful scoped reads, changed company identity, missing GUIDs, empty versus missing data, unknown compound quantities, malformed responses, Tally errors, timeouts, redirects, UTF-16 and response-size limits. They establish adapter behaviour under those fixtures. No test currently proves the projection or closing-balance period semantics against a running Tally installation.

On 20 November 2026, discovery from a fresh live Windows workspace could not connect to the local Tally listener on port 9000. Connections reported the failure and the company selector stayed empty. No real company balance, ledger or sales voucher was available to compare on this machine.

On the customer installation, compare quantities with the same company and date in Tally and verify the effects of sales, purchases, receipt notes and stock adjustments. The current reader reports the whole company balance. Map it only to a Flipkart location supplied by that entire balance and confirm the Tally base unit when choosing Set of. Sellers who need an individual godown balance must wait for an explicitly scoped godown reader.

Blank, unsupported or mismatched units produce an unknown quantity (`null`), not zero. Missing or invalid envelopes reject the complete read so the application can preserve its last valid observation. Negative numeric stock is preserved as source data; the separate stock policy decides its advertised effect.

## Ledger and sales bill evidence

Ledger discovery returns the current name and GUID from the selected Tally company. A billing read resolves the saved ledger GUID to its current name, requests vouchers for that ledger and date range, and checks the returned company and ledger projections. The ledger name is passed as a value. Tally documents the [ledger voucher collection and nested inventory fields](https://help.tallysolutions.com/how-to-choose-the-right-approach-from-tdl/) and [sales voucher type test](https://help.tallysolutions.com/what-are-objects-and-collections-related-functions-in-tdl/). The posted sales projection excludes cancelled, optional and postdated entries.

A selected party ledger applies to the invoice. A selected sales ledger must appear in the item's accounting allocation, so a mixed invoice contributes only the lines posted to that ledger. The bill reader returns its GUID, date, voucher number, Reference and Narration. Actual outward quantities are grouped by verified stock-item identity and Tally base unit. Accounting-only entries, unsupported quantities, and delivery-note-linked invoices do not supply matching evidence. Tally documents the separate [actual and billed quantities in invoice XML](https://help.tallysolutions.com/sample-xml/) and the workflow where a [delivery note updates inventory separately from the sales invoice](https://help.tallysolutions.com/delivery-note/).

The adapter tests use constructed local HTTP responses. On the seller's installation compare one ordinary posted item invoice with the matching stock movement and test a shop sale, a cancelled sale, and any custom sales voucher or delivery-note workflow in use. Confirm the reference field returned for that company and compare dates, ledger identity, item units and actual quantities. A ledger bill by itself does not establish that Flipkart received an order.

For an order with a mistyped Flipkart reference, look up the printed Tally bill number and compare the voucher GUID, date, ledger and actual outward units. Check whether a competing order identifies the same deduction. A seller-confirmed link should release only the selected order item's reservation on the next verified calculation. Include an amended voucher and a second order for the same stock item when validating this flow on customer data.
