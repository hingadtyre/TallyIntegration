# First-customer release readiness

**Audit date: 2026-11-08. Status: read-only pilot; complete customer release not ready.**

This is the readiness checklist for the first customer delivery. The [approved architecture](design/architecture.md#customer-release-completion) defines the required behavior; [README](../README.md) describes the delivered build; [customer setup](customer-setup.md) describes the available operating steps. Test fixtures establish local behavior, not a live Tally or Flipkart connection.

## Current deliverable

The application can discover and read company-wide Tally stock, keep companies separate, display observations, prepare and retain local proposals, review their captured scope, preserve Pause and existing policies, save polling settings, record activity/diagnostics and create verified manual SQLite backups. A technician-assisted offline pilot restore validates backup identities/integrity, requires a preview digest, preserves current local settings and creates a safety copy before replacement. Restored observations require fresh reads, automation is disabled and listings are paused. Tally transport remains read-only. Marketplace publication is explicitly rejected and `publishingEnabled` remains false. [Tally adapter](../src/adapters/tally.ts), [inventory service](../src/server/service.ts), [HTTP routes](../src/server/http.ts), [backup manifest](../src/server/backups.ts), [pilot restore](../src/server/restore.ts)

The [tests](../tests/) exercise these behaviors through local HTTP responses, isolated databases and browser simulations. The pure [allowance helper](../src/domain/allowance.ts) is tested accounting arithmetic; it is not a delivered order importer or durable allowance-activation workflow. A saved draft does not authorize or change marketplace stock.

**Portable pilot packaging: implemented and locally verified on Windows x64, 2026-11-08.** The 0.1.0 pilot bundles Node v24.22.2, a persistent data directory outside the extracted application, an offline HTML guide and double-click start/stop/status launchers. The full source verification passed 145 tests, formatting, lint and build. The extracted ZIP passed 16 additional package checks using only its bundled runtime, from an unrelated working folder with no Node/npm on the search path. The checks covered file hashes/runtime dependencies, empty live state, dashboard assets, repeated Start, local simulated Tally import, saved settings, verified backup, authenticated shutdown, refusal to restore while running, offline restore and restart/persistence. The final stop removed its control record and released the dashboard port. [Reproducible verification](../CONTRIBUTING.md#build-the-windows-pilot-package), [package checker](../scripts/verify-pilot.mjs)

Each build has a timestamped filename, a manifest with its commit/uncommitted-change indicator and file hashes, and a ZIP checksum sidecar. Each extracted check retains its exact artifact/checksum and outcome in an ignored `releases/verify-pilot-*/verification.json` receipt. Retain that receipt with the chosen artifact; do not treat a different ZIP as verified. The offline guide's internal links were checked, but a visual browser preview and customer-machine installation have not been verified. A portable pilot alone does not provide a signed Windows installer, automatic startup/restart, controlled upgrades or the missing marketplace workflows. Offline pilot restore is not production order/policy reconciliation.

## Application work that can proceed without customer access

| ID    | Missing production behavior                                 | Required completion evidence                                                                                                                                                                                                                                                                                                                                                                  |
| ----- | ----------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| APP-1 | Provider authorization service and local connection journey | Implement installation-bound consent, state validation, isolated seller grants, protected credentials, expiry/renewal, disconnect/reconnect and understandable failure/retry states. Exercise successful, denied, expired and mismatched callbacks with controlled fixtures. Keep the shared provider secret out of every customer package and backup.                                        |
| APP-2 | Authenticated seller, listing and marketplace stock import  | Implement complete pagination, unavailable/invalid records, seller isolation and stable IDs. Preserve distinct location observations and timestamps; handle partial reads without inventing zero. Validate the contract uncertainties tracked under EXT-3.                                                                                                                                    |
| APP-3 | Source-location and pack verification                       | Implement explicit Tally godown-to-marketplace-location mapping, verified sellable pack evidence and invalidation after metadata changes. Company-wide balances and SKU/title guesses are insufficient. Apply the accepted tyre advertising rule only in its approved customer/category scope.                                                                                                |
| APP-4 | Reviewed manual publication and recovery                    | Persist exact destinations and publication attempts; revalidate source/mapping/policy versions before sending; inspect each SKU result; read back changes; reconcile timeouts, partial results, restart and superseded work. A successful HTTP response alone must not activate a policy or report confirmed stock.                                                                           |
| APP-5 | Order reconciliation and active sales allowances            | Implement durable order receipts, activation baselines/generations, complete page/time coverage and transactional deductions for the exact seller/listing. Repeat observations and later Tally billing must not deduct twice; cancellations, returns and purchases must not refill allowance. Cover orders arriving during activation and recovery.                                           |
| APP-6 | Automatic publication, Pause and safe unlink                | Implement durable scheduling/publication without overlap, stale-source protection and reviewed resume. Pause blocks every automatic write while observations/accounting continue. Complete zero-and-verify unlink and preserve the explicit leave-stock-unchanged alternative.                                                                                                                |
| APP-7 | Production installation and recovery                        | Deliver the customer package, stable data/credential ownership, automatic background startup/restart, one process per workspace, scheduled verified backups, retention, safe restore, compatible upgrades and data-preserving uninstall. Test interruption, failed migration, corrupt restore and restore of exhausted allowances. Portable pilot verification is only a subset of this work. |

These are implementation gaps, not tasks deferred until the customer's Tally computer is available. Their rules and acceptance cases are in the [architecture](design/architecture.md#key-acceptance-scenarios). Existing local inventory features remain useful while this work is completed.

## External provider and account gates

| ID    | External prerequisite                 | Evidence needed before live activation                                                                                                                                                                                                                                                                                               |
| ----- | ------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| EXT-1 | Flipkart partner/application approval | Provider completes API-partner verification and third-party application registration. Record the approved application identity and environment without recording its secret. No approval or registered application is evidenced in this repository.                                                                                  |
| EXT-2 | Hosted authorization deployment       | Provider supplies hosting, domain/callback and operational ownership. Deploy the implemented service over HTTPS with protected secrets and verify the registered callback end to end. A localhost dashboard or locally passing callback test is not deployment evidence.                                                             |
| EXT-3 | Approved account and API contracts    | Obtain authorized access and resolve seller identity for empty accounts, location discovery, listing response inconsistencies, inventory/pending-inventory meaning and order-history/time-window guarantees. Record sanitized real response evidence or provider clarification; do not invent undocumented endpoints or identifiers. |
| EXT-4 | Customer consent and isolation        | Customer authorizes the provider application using their own Flipkart account. Verify authenticated seller/location identities, installation binding, renewal and revocation/reconnection. The HINGADTYRES browser display name is historical context, not authenticated evidence.                                                   |

The verified public requirements and API references are in [onboarding research](integration/customer-onboarding-research.md). The accepted model is [provider-managed authorization](adr/0003-provider-managed-flipkart-authorization.md). It does not require Stockbridge invitations, activation codes, separate customer signup, or manual provider approval of each installation. Flipkart's required partner approval and each seller's consent still apply.

## Evidence required for handoff

1. Record the package filename/version/checksum, bundled runtime and validated data/launch behavior. For the pilot, clearly state that Flipkart connection/publication and automatic Windows lifecycle remain unavailable.
2. Record the final formatting, lint, tests and build results for that exact change. Include focused failure/recovery scenarios for implemented workflows; do not equate a test count with customer release completion.
3. Resolve APP-1 through APP-7 before calling the product the complete first-customer release. Record EXT-1 through EXT-4 and CUSTOMER-1 through CUSTOMER-4 before enabling routine live publication.
4. Keep [customer setup](customer-setup.md), in-app guidance and [README](../README.md) aligned with the verified artifact and remaining limits. Update this audit when evidence changes; a settings field, draft UI or fixture is not proof that a missing integration works.
