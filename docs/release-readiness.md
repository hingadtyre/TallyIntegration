# First-customer release readiness

**Audit updated 2026-11-20. The pilot supports mapped Tally-to-Flipkart stock synchronization. Customer installation and a live stock write still require acceptance.**

This is the readiness checklist for the first customer delivery. The [approved architecture](design/architecture.md#customer-release-completion) defines the required behavior; [README](../README.md) describes the delivered build; [customer setup](customer-setup.md) describes the available operating steps. Test fixtures establish local behavior, not a live Tally or Flipkart connection.

## Current deliverable

The application can discover and read company-wide Tally stock, keep companies separate, display observations, prepare and retain local proposals, review their captured scope, preserve Pause and existing policies, save polling settings, record activity/diagnostics and create verified manual SQLite backups. A technician-assisted offline pilot restore validates backup identities/integrity, requires a preview digest, preserves current local settings and creates a safety copy before replacement. Restored observations require fresh reads, automation is disabled and listings are paused. Tally transport remains read-only. Inventory can publish a reviewed proposal, synchronize eligible listings after a Tally stock change, and lower shared listings when Stockbridge verifies a Flipkart sale. Customer acceptance should compare a single-tyre sale with the pair listing before billing and verify seller-reviewed recovery on a specifically authorized test destination. The seller chooses a package-based or manual Set of for each destination and explicitly confirms the company balance supplying it. [Tally adapter](../src/adapters/tally.ts), [inventory service](../src/server/service.ts), [HTTP routes](../src/server/http.ts), [backup manifest](../src/server/backups.ts), [pilot restore](../src/server/restore.ts)

The [tests](../tests/) exercise these behaviors through local HTTP responses, isolated databases and browser simulations. The pure [allowance helper](../src/domain/allowance.ts) is tested accounting arithmetic; it is not a delivered order importer or durable allowance-activation workflow. An Inventory draft does not authorize or change marketplace stock. In the separate Marketplaces view, live Apply sends a real edit and requires a fresh readback before reporting Updated.

The new Marketplaces view implements multiple explicitly added accounts, separate Windows-protected credentials, complete listing imports, seller binding and stock/MRP/selling-price Apply with durable attempts and readback. New live workspaces start with Add account; legacy saved primary credentials are adopted in place. Complete import must verify seller identity after restart or credential operations before Apply or Check result. A changed seller or duplicate seller account is rejected; an empty account cannot establish a new identity. Sample mode never contacts Flipkart. [Account service](../src/server/marketplace-service.ts), [publication](../src/server/marketplace-publication.ts), [adapter](../src/adapters/flipkart-listings.ts)

Holds and allowances remain effective. Positive live stock under Limited sales is blocked until order reconciliation exists or an explicit Auto policy change removes that destination's constraint. Pause remains separate. Incomplete direct attempts become uncertain after restart without replay. Schema 4 persists mapping choices, package evidence and pending Tally changes. Earlier supported schemas are backed up before migration. Offline restore retains seller bindings, clears freshness and marks unfinished attempts uncertain; this does not implement production order reconciliation.

## Customer-machine acceptance evidence

Order matching supports seller-selected ledgers, per-account reference rules, recent order and voucher previews, and manual confirmation or release. After the seller confirms order coverage, calculated publication checks unbilled base units across participating accounts. Local scenarios cover a purchase before billing, the subsequent bill, duplicate observations, different pack sizes and incomplete reads. Customer acceptance still requires comparing Seller Hub order coverage and actual stock-affecting Tally entries for the same dates, then observing one specifically authorized write and readback. Include an ambiguous bill, a shop sale, a return, a seller cancellation and sales arriving during synchronization. Finite sales allowance activation remains a separate delivery gate.

2. Record the final formatting, lint, tests and build results for that exact change. Include focused failure/recovery scenarios for implemented workflows; do not equate a test count with customer release completion.
3. Resolve APP-1 through APP-7 before calling the product the complete first-customer release. Record the applicable EXT-1 through EXT-4 gates and CUSTOMER-1 through CUSTOMER-4 before enabling routine live publication.
4. Keep [customer setup](customer-setup.md), in-app guidance and [README](../README.md) aligned with the verified artifact and remaining limits. Update this audit when evidence changes; a settings field, draft UI or fixture is not proof that a missing integration works.
